## Access and authority

- **HTTP-001 — Authorized domain dispatch** (done). Every proposal, client, import and invoice handler checks a native Base owner or member session, or a revocable owner-bound agent key, before it reads or writes. Browser mutations require the configured Origin and Host and refuse cross-site requests. Which role may take which action is `TEAM-001`, with approving and sending set by `APPROVE-003`; every refusal is a 403 with no write. Signed-out readers of `/app` are sent to sign-in, and unknown routes return real 404s. **Acceptance evidence:** Through HTTP: read state signed out (401), post a mutation from a foreign Origin (403), call a domain command with a revoked agent key (401) and as a member for an owner-only action (403). Evidence: `tests/platter.test.mjs`, `src/platter/http.ts`
- **ACCESS-001 — Revocable agent keys that only draft** (done). An owner issues an agent key with a label and a 30-day expiry, stored only as a hash and bound to that owner's current account version. An agent key can read context and prepare or revise drafts, and nothing else: it cannot add clients, approve prices, send offers or export invoices. Revoking the key, or the owner losing the owner role, ends its access at once. Drafts an agent prepares are attributed to the key, and a draft prepared or last revised by an agent key always needs a person's approval before it is sent (`PROP-001`), even where the approval policy lets proposals that match no rule go without one (`APPROVE-003`). **Acceptance evidence:** Create a key, prepare a draft with it, try to approve and add a client with it (403), revoke it, and read context with it again (401). Evidence: `tests/platter.test.mjs`, `src/platter/credentials.ts`

## Approval, sending and acceptance

- **PROP-001 — Approval binds the exact revision** (done). Every approval names one exact revision. Saving a new revision clears every approval the proposal holds, so a changed price, scope or term can never be sent on an earlier approval, and each approval is recorded with its approver, role, rule, revision and time. Who may approve and send, and which proposals need approval at all, is the approval policy of `APPROVE-003`. Its default, which every installation starts with and keeps until the owner changes it, is the first release's rule: every proposal needs approval, and only a person with the owner role approves. A draft prepared or last revised by an agent key (`ACCESS-001`) always needs a person's approval, whatever the policy says. `APPROVE-001` and `APPROVE-003` decide which approvals apply; neither can remove the exact-revision binding. **Acceptance evidence:** Under the default policy: approve a stale revision (409), approve the current one as the owner, revise the price, try to send (409), approve the new revision and send; two approval records exist, each naming its revision. - **PROP-002 — Sending freezes the offer** (done). Sending freezes the approved revision: its scope, options and prices can no longer be edited in place.
