# SMS, personal notifications and signer methods

These native interfaces are available through the authenticated command endpoint at `/api/platter/command`. Send JSON with `name` and `input`, the current person's session, and this installation's Origin. Agent keys cannot configure or send SMS or choose notification preferences.

## Text messages

The runtime needs the private `TWILIO_ACCOUNT_SID` and `TWILIO_AUTH_TOKEN` bindings and the `TWILIO_FROM` sender binding. The native installer offers an optional Twilio choice and requires all three inputs when selected; leaving SMS disabled prevents text transport even if private credentials remain saved. The owner deployment declaration carries these optional bindings privately. Configure the same optional inputs in managed hosting. Production delivery requires the owner's registered US A2P or toll-free sender; provider-fake tests do not qualify a sender or establish carrier compliance. Development mode suppresses SMS transport. Configure the inbound Twilio webhook to `/api/platter/sms/inbound` and delivery callbacks to `/api/platter/sms/status` on the installation's HTTPS origin. Both require Twilio's account-bound HMAC signature; callbacks cannot activate consent.

For a text-only invitation, choose “Prepare text-only invitation” in the invitation delivery control, or pass `delivery: "sms"` to `proposal.send`. This prepares the approved link without queuing or sending email; it grants no SMS consent. Email remains the default. Then use `sms.configure` with its `id`, current `version`, `consent: true`, exact invitation `recipient`, normalized US `phone`, sending `firm`, permitted `purposes`, exact `disclosure` shown, `assentedAt` including its UTC offset, collection `method`, recipient-supplied IANA `timeZone`, and recipient `evidence` supporting the entry. Select purposes independently from `invitation`, `reminder`, `identity` and `completion`. The proposal’s SMS Settings expose the same inspect, record and revoke controls. Each entry is immutable; revocation preserves history and cancels pending texts. Only a person with current Send authority can do this. No number or zone is inferred. Consent belongs to that exact revision and invitation. Reissuing an invitation requires fresh consent. Restored consent is historical and cannot send.

Use `sms.send` with `id`, `message` and a unique `requestId`. The default kind is `invitation`; `kind: "manual"` requests a reminder. Platter adds the current invitation link and STOP and HELP instructions. A repeated request id returns the original attempt; changed text is refused. A manual reminder is limited to one per recipient calendar day. Quiet-hour messages wait for the next allowed time. Scheduled texts use the existing explicitly authorized reminder schedule, matching supplied recipient zone and cap. Disabling or changing the schedule prevents its queued texts from sending.

`GET /api/platter/sms?id=…` returns the consenting person's record and the proposal's link-free message history to its current senders. Bearer invitation links and credentials are transport-only. Provider acceptance is distinct from delivered; signed callbacks update delivery status without regressing a terminal receipt. Uncertain sends remain held, without automatic retries. Withdrawal atomically cancels queued messages. Acceptance, decline and expiry prevent later invitation and reminder texts; completion uses its separate assent and readiness grant. Lost authority, invitation rotation and STOP prevent every later purpose. STOP applies to the number, including other proposals; START never restores sending authority. HELP returns sender-support instructions. STOP does not change email preferences.

The 26 October ct ruling approves this consent policy, without qualifying a sender or certifying carrier or legal compliance. A newly signed single-recipient agreement creates a local completion grant only when the current assent explicitly permits completion. Completion sends once after any required deposit is both confirmed and exactly authorized by the client, using the same quiet hours, live sender checks, suppression and uncertain-outcome hold as other texts. Reminder-only opt-out leaves separately permitted completion active. Restores retain completion history but exclude its execution grant; no historical agreement creates a new grant. SMS currently uses the single invitation recipient; configured recipient plans retain their mailbox checks under SIGN-006. Safe re-enablement is owner-only. An account-bound, signed Twilio Advanced Opt-Out `OptOutType: START` receipt records provider eligibility for the currently suppressed number and transport. Plain START does not. Neither event removes suppression or creates sending authority. The owner separately records new assent after the STOP, confirms suppression removal explicitly and authorizes only the current invitation through `sms.reenable`. The immutable history retains the STOP source and time, provider receipt, fresh assent and actor. Other invitations stay inactive. Later STOP invalidates eligibility; a replayed provider receipt cannot cross it. Restores retain receipt and action history but exclude provider eligibility and all operational authority. See [Twilio’s Advanced Opt-Out documentation](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out) for the required Messaging Service configuration; where that authenticated receipt is unavailable, re-enablement is refused. Real sender registration, carrier acceptance and legal qualification remain unproved.

## Personal activity notifications

Use `notification.watch` with proposal `id`, preference `version` (zero initially), explicit `consent: true`, boolean `email`, and `events` selected from `view`, `comment`, `signed`, and `paid`. An empty event list disables these notices. View alerts additionally require the current owner to opt in for that revision; owner revocation stops them for every watcher, and no pre-consent view is replayed. Each person manages only their own preferences and must currently see the proposal. Preferences bind to the current revision; changing them starts from current events without replaying older activity.

An optional `slackRoute` must name an active, admin-verified direct Slack route for that same person. Configure it through the existing `notification.route` interface; a channel or another person's direct route is refused. Other explicitly configured notification routes keep their own purposes and consent. Email goes only to the active person's sign-in address. `GET /api/platter/watch?id=…` reads that person's preferences.

The Worker scheduler queues the first client view, client questions, signatures and verified received-payment records once per watcher and carrier. Notices contain generic event text and a session-protected proposal link, without proposal content, question text, prices or recipient credentials. Losing proposal scope, changing preferences, disabling the route or restoring an archive prevents queued outbound work. Provider uncertainty is held, not retried automatically. Decline and failed-payment events, personal Teams, Nook and push preferences, and a preference screen remain unfinished.

## Text-code signing and retained certificates

Mailbox code remains the default. A current sender selects `signer.method` with proposal `id`, current `version`, and `method: "SMS code"` only after recording the SMS consent above. The current invitation must not already have requested or verified a code; reissue before changing an identity check already in use. The existing client form then requests and verifies a text code. Codes expire after ten minutes, permit five wrong attempts, require a minute between generations, have a ten-generation limit and are single use. Quiet hours and STOP apply. A changed SMS consent record invalidates outstanding text verification.

New signatures retain their actual method, verification time when known, acceptance time and consent. Completed single-client agreements expose `/p/<invitation>/agreement.pdf`, `/p/<invitation>/certificate.pdf` and `/p/<invitation>/certificate.json` to the verified signer. Current scoped people can use the corresponding `/api/platter/` download routes with proposal `id`. The client page links the PDFs. A required deposit must be complete first. The immutable signed PDF hash matches the certificate; the same bytes are retained in archives. Historical signatures without retained method facts are refused rather than assigned a method retroactively. Location and user agent are explicitly labelled not recorded.

Multiple signers, ID verification, link-only signing, completion email attachments and full certificate metadata remain unfinished. The consent default also applies to SMS identity verification pending ct approval.
